No throwaway or lab launchd jobs were created. Home paths are elided to ~ and the remote Firstmate home to <remote-home>.

Summary of what happened:
1. Read-only (full-1): launchagent=fixable and remote-job-worker=fixable. Both base-written agents read out of contract, and the fix hint names "process type".
2. --fix (full-2): both agents were rewritten with ProcessType=Interactive.

   - The Herdr agent was booted out, but its bootstrap was refused with "Bootstrap failed: 5: Input/output error", so launchagent-loaded and herdr-server stayed fixable. The doctor's reload_launch_agent runs bootstrap right after bootout, without the bootout-cleanup wait the remote-job library uses.
   - Within seconds the host's own base-code entrypoint reverted the job agent to the base template. The supervising firstmate polls the host every few seconds, and each routed command runs fm_remote_job_ensure_worker against the host's older template.
3. --fix retry (full-3): the job agent was rewritten and reloaded again, and again reverted by the host's own polling-driven ensure. A worker killed mid-start during these competing reloads left only zero-byte temp files (.pid.*, .start.*, .command.*) in worker.lock. The worker's dead-owner reclaim removes pid, start and command but not those temp files, so its rmdir fails and every respawn exits ("cannot acquire or safely reclaim worker ownership"). This is a separate, pre-existing reclaim bug present in base and head.
   Herdr launchagent-loaded and herdr-server were still fixable.
4. Restore with the host's own doctor --fix, routed through fm-on.sh (full-4): the Herdr agent was rewritten to the base template (sha256 identical to before), bootstrapped and started (server running in Aqua). The job worker stayed wedged on the stale lock.
5. Stale lock repair (full-5): after confirming no worker process was running and the three files were zero bytes, they and the lock directory were removed. launchd restarted the worker.
6. Confirmation (full-6): the host's own doctor reports "remote second-mate readiness confirmed on this host". Both agents are byte-identical to their starting files.

What this does and does not show:
- Shown live: base-written agents read out of contract (both), and --fix rewrites both with ProcessType=Interactive. The remote job agent reached ready.
- Not reached live: the Herdr agent reaching ready under this branch. Its bootstrap failed with I/O error 5 immediately after bootout, on both the first pass and the retry, while the job agent was being reloaded concurrently.
- Not representative of a normal upgrade: the competing reloads came from running a newer doctor against a host whose own code root was still older. In a real upgrade the host's code root carries the new template, so its routed ensure agrees with the doctor.
- The host was restored to its starting state afterward.
